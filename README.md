# 항공권 예매 서비스

기존 프론트 시안에 함께 반영한 주요 기능과 백엔드 구현, 실행·테스트·배포 방법을 정리함. 프론트·백엔드 안내는 이 문서에서 함께 관리하며, 상세 요청·응답 명세는 실행 중인 백엔드의 `/docs`에서 확인함.

## 1. 프로젝트 구성

```text
항공권 예매 서비스/
├─ frontend/
│  ├─ README.md             # 통합 안내 문서
│  ├─ src/                  # 화면·컴포넌트·API 연결
│  ├─ public/               # PWA 아이콘 등 정적 파일
│  ├─ tests/                # 프론트 자동 검사
│  ├─ .env.example
│  ├─ package.json
│  ├─ vite.config.js
│  └─ vercel.json
└─ backend/
   ├─ app/
   │  ├─ routers/           # API 경로·요청 처리
   │  ├─ services/          # 검색·예약 등 업무 처리
   │  ├─ integrations/     # Gemini 연결
   │  ├─ schemas/          # 요청·응답 검증
   │  ├─ models/           # DB 모델
   │  └─ core/             # 환경설정·DB·인증
   ├─ database/             # 스키마·시드·조회 예제 SQL
   ├─ 챗봇_테스트_정리.txt
   ├─ .env.example
   └─ requirements.txt
```

React·Vite 프론트, FastAPI·SQLAlchemy 백엔드, MySQL로 구성함. 프론트는 API만 호출하며 DB와 Gemini에는 백엔드가 접속함. 아래 명령은 각 절에 명시한 폴더에서 실행함.

## 2. 정리한 주요 내용

### 항공편 검색과 노선 안내

- 편도·왕복 검색을 실제 API와 연결함. 도시·국가·공항명·IATA/ICAO 코드 자동완성과 공항·도시명 표시를 지원함.
- 날짜·시간·좌석 등급·가격·항공사 조건과 정렬을 연결함. 항공사 필터 목록은 현재 검색 조건에 맞는 결과를 기준으로 제공함.
- 왕복 검색은 출발·도착 공항이 서로 반대이고 귀국편이 가는 편 도착 이후인 조합을 조회함.
- 왕복 시간 필터를 가는 편·오는 편으로 구분함. 상단의 가는 날·오는 날은 각 구간의 출발 날짜이며, 도착 시간대도 기본적으로 해당 날짜를 기준으로 적용함. 다음 날 도착하는 경우에만 ‘도착일이 출발일과 다른 경우’를 펼쳐 날짜를 변경함. 상단 날짜 변경 시 별도 도착 날짜는 초기화함. 시간대 변경은 ‘필터 적용’ 또는 ‘검색하기’로 반영함. 모든 시간은 한국 시간 기준이며 왕복 정렬의 출발순은 가는 편, 도착순은 오는 편 기준임.
- 인기 노선은 최근 30일 예약 기록을 기준으로 챗봇에서 안내함. 회원의 자주 이용한 노선은 완료된 탑승 기록을 기준으로 제공함. 취소 예약과 결항편을 제외함.
- 진행 중인 프로모션을 메인 화면에서 안내함. 2개 이하는 고정 표시하고, 그보다 많으면 순환 표시함.

### 좌석 선택·예약·취소

- 좌석 선택 → 예약 정보 입력 → 예약 확인 흐름을 편도·왕복 모두 지원함. 좌석 등급별 탭, 예약자 정보의 탑승객 입력란 복사, 모바일 하단 고정 요약·확장 패널을 적용함.
- 왕복은 탑승객마다 가는 편·오는 편 좌석을 연결하며, 기존 예약·예약 상세 테이블로 두 구간을 저장함. 별도 왕복 테이블을 추가하지 않음.
- 좌석 중복 선택과 예약 가능 여부를 서버에서 확인함. 좌석·회원 포인트 등 경합 가능한 데이터를 트랜잭션에서 처리하며, 왕복 중 한 구간에 실패하면 전체를 되돌림.
- 예약 재전송에는 중복 방지 키를 사용함. 동일한 예약의 재시도로 예약이 중복 생성되지 않도록 처리함...
- 금액·할인·포인트는 서버에서 계산함. 비회원은 프로모션을 선택할 수 없으며, 직접 API로 요청해도 적용을 거절함.
- 회원·비회원 예약 조회와 취소를 연결함. 왕복 취소는 두 구간을 함께 처리하며 좌석과 포인트 내역을 반영함.

### AI 챗봇과 조건 기반 조회

- Gemini가 사용자 질문을 의도·검색 조건 JSON으로 변환하고, 백엔드가 검증한 조건으로 SQLAlchemy 조회를 구성함. 안전을 위해 모델이 반환한 임의 SQL을 실행하지 않음.
- 최근 대화를 지원하며 날짜·도착지 변경, 항공사 제외 등 후속 질문을 처리함. 모호하거나 지원하지 않는 요청은 추가 질문 또는 안내로 응답함.
- “오는 편만 저녁으로”처럼 귀국편 조건만 변경할 수 있음. 아직 합의하지 않은 오전·오후·저녁·새벽은 한국 시간의 구체적인 범위를 확인한 뒤 조회함. “네”로 수락하면 확인 대기 조건을 적용하고, 거절하면 기존 확정 조건을 유지함. 귀국일 변경 시 귀국편 시간 범위만 이동하며, 편도로 변경하면 귀국편 조건을 해제함.
- “프로모션이 알고 싶어”로 주제를 바꾸면 프로모션만 안내함. 이전 항공편 검색 조건은 후속 질문을 위해 보관하되 항공편과 프로모션을 함께 요청한 경우에만 함께 조회함. 현지 시간 변환은 지원하지 않으며 한국 시간 입력을 안내함.
- 편도·왕복 항공편, 진행 중인 프로모션, 회원 등급, 인기 노선과 회원별 자주 이용한 노선을 안내함. 문의 관련 질문은 문의 화면으로 안내하며 챗봇이 문의글이나 예약을 직접 등록하지 않음.
- 프론트에는 팝업 채팅창, 응답 유형별 결과·이동 버튼, 후속 질문, 대기·타이핑 효과를 적용함. 타이핑은 화면 효과이며 서버 스트리밍은 사용하지 않음.
- 항공편 결과는 처음 3건을 표시하고 더 보기로 이미 받은 결과를 펼침. 더 보기 때문에 AI API를 다시 호출하지 않음.
- 호출 제한·타임아웃·읽기 전용 DB 조회를 적용함. 일단 LangChain이나 벡터 DB는 사용하지 않음(소규모).

### 왕복 시간 조건 연결

`GET /api/flights/round-trips`와 챗봇의 `interpreted_conditions`에서 다음 조건을 사용함. 각 `from`·`to`는 한국 시간의 날짜와 시각을 포함하며, 값이 없으면 해당 제한을 적용하지 않음.

| 조건 | 기준 |
|---|---|
| `date`, `departure_from`, `departure_to` | 가는 편 출발일·출발 시간 범위 |
| `arrival_from`, `arrival_to` | 가는 편 도착 시간 범위 |
| `return_date`, `return_departure_from`, `return_departure_to` | 오는 편 출발일·출발 시간 범위 |
| `return_arrival_from`, `return_arrival_to` | 오는 편 도착 시간 범위 |

예: `return_date=2026-12-17`, `return_departure_from=2026-12-17T18:00:00`, `return_arrival_to=2026-12-18T06:00:00`이면 17일 저녁 출발·18일 오전 6시까지 도착하는 귀국편을 조회함. 왕복 예약 API와 테이블 구조는 동일함.

### 회원 혜택 안내

- `/benefits`는 로그인 없이 접근 가능한 혜택 페이지임. 기존 `/grades`, `/promotions` API로 등급별 적립률과 현재 진행 중인 프로모션을 표시함. 로그인 시 현재 등급·보유 포인트를 함께 안내함.
- 상단 ‘혜택’ 메뉴, 마이페이지의 등급 안내, 메인 프로모션에서 연결함. 예약 화면의 안내 링크는 입력 중인 정보를 유지하도록 새 창으로 열림.
- 등급별 할인이나 자동 승급을 새로 구현하지 않음. 현재 백엔드 정책에 맞춰 등급별 포인트 적립, 예약 한 건당 프로모션 한 개, 할인 후 포인트 사용 및 최종 결제액 기준 적립을 안내함.
- 등급·프로모션 조회 실패를 개별 처리하며 재시도 버튼을 제공함. 프로모션이 없는 경우 별도 안내를 표시함.
- 배경 이미지: [Joshua Tsu의 Moraine Lake 사진](https://unsplash.com/photos/ifHBo0TTuBI), [Unsplash License](https://unsplash.com/license). 무료 사용 가능 여부를 확인하고 `public/images/benefits-lake.jpg`로 보관함. 장식용 여행 이미지이며 특정 노선 할인 대상이라는 의미는 아님. PWA 정적 자산에도 포함함.

### 귀국 날짜 범위 검색

챗봇에서 조건 없이 새 검색을 요청하면 조회를 실행하지 않고 이전 검색 조건을 초기화한 뒤 새 조건 입력을 안내함. 화면의 기존 대화는 유지하지만 초기화 이전 대화는 다음 검색의 문맥으로 전달하지 않음.

- `GET /api/flights/round-trips`에서 출국 `date`는 하루로 지정함. 귀국은 기존 `return_date` 또는 `return_date_from`·`return_date_to`로 지정함. 단일 날짜와 기간을 동시에 보내지 않음.
- 기간은 양 끝 날짜를 포함하며 최대 30일임. 종료일을 생략하면 시작일부터 30일간 조회함. 예: `date=2026-11-25&return_date_from=2026-11-26`은 11월 25일 출국과 11월 26일~12월 25일 귀국편 출발을 조합함. 출국편 도착 이전에 출발하는 귀국편은 제외함.
- `sort_by=return_departure_at&sort_order=asc`는 귀국편의 빠른 출발순임. 기존 `departure_at`은 출국편 출발순, `arrival_at`은 귀국편 도착순임.
- 모든 날짜·시각은 한국 시간 기준임. 날짜 기간과 별도 시각 조건을 함께 지정하면 두 조건을 모두 만족하는 항공편만 조회함. 기간 내 매일 반복되는 오전·저녁 시간대 조건은 지원하지 않음.
- 챗봇은 “26일 이후 돌아오는 항공편”을 귀국 출발 기간으로 검색하고 실제 조회 기간을 응답에 안내함. 월을 생략한 날짜는 확정된 여행 월을 우선하고, 이전 일정이 없으면 이번 달로 해석함. 지난 날짜를 임의로 다음 달로 넘기지 않음.
- 일반 검색 화면의 기존 날짜 선택은 그대로 유지함. 범위 검색은 API와 챗봇에서 사용 가능하며, 예약 API·DB 테이블은 변경하지 않음.

챗봇 시간 확인 응답은 `needs_clarification`과 `reason=time_confirmation`으로 반환함. 프론트는 반환된 `context`를 다음 요청에 그대로 전달함. `context.pending_search`는 확인 대기 조건이며, 수락 전에는 검색을 실행하지 않음. Gemini에는 간소화한 생성 스키마를 전달하고, 실제 반환값의 길이·개수·금액 등 세부 제약은 서버에서 검증함.

### 회원·문의·관리자와 코드 구조

- JWT 인증과 회원·관리자 권한 검증을 적용함. 비밀번호는 해시로 저장하고, 회원·비회원 조회 경로에서 본인 확인 조건을 검증함.
- 문의 작성과 비회원 문의 조회를 탭으로 구분하고, 회원 문의 내역·관리자 답변을 연결함.
- 관리자 항공편 등록·수정·좌석 생성, 예약 조회, 문의 답변, 프로모션 등록·수정·삭제를 연결함.
- 백엔드의 예약 처리·반복 조회를 서비스로 분리하고 입력 검증과 파라미터 기반 조회를 정리함. 프론트의 API 요청, 날짜·금액 표시, 예약 요약, 탭과 관리자 화면을 역할별로 분리함.

### PWA

- 비행기 아이콘(SVG)과 manifest·서비스 워커를 구성하여 설치 가능한 앱 형태로 빌드함.
- 정적 화면 파일만 캐시함. API 응답·예약 데이터를 서비스 워커에 저장하거나 실패한 예약·문의를 자동 재전송하지 않음.
- 새 버전은 업데이트 안내 후 사용자가 새로고침할 때 적용함. 검색·예약·문의·챗봇은 온라인 연결이 필요함.

고려사항으로 특정 국가·항공편에만 적용하는 프로모션, 검색 결과의 할인 운임 표시는 구현하지 않음. 추후 추가가능성

## 3. 최초 DB 구성

Python 3.13, Node.js 24.x, MySQL 8 이상을 기준으로 함. 이미 사용 중인 DB가 있다면 스키마·전체 시드를 다시 적용하지 않고 연결 설정만 확인함.

`backend` 폴더에서 MySQL 관리자 계정으로 접속함.

```powershell
mysql --default-character-set=utf8mb4 -u root -p
```

최초 구성 시 DB와 앱 계정을 생성함. 아래 비밀번호는 실제 사용할 값으로 변경함. 계정이 이미 있으면 `CREATE USER`를 반복하지 않고 기존 권한을 확인함.

```sql
CREATE DATABASE IF NOT EXISTS airline_reservation
  CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci;

CREATE USER 'airline_app'@'localhost'
  IDENTIFIED BY 'REPLACE_WITH_A_STRONG_PASSWORD';

GRANT SELECT, INSERT, UPDATE, DELETE
  ON airline_reservation.* TO 'airline_app'@'localhost';

SOURCE database/schema.sql;
SOURCE database/seed_reference.sql;
SOURCE database/seed_demo.sql;
```

`SOURCE`는 MySQL 명령창에서 실행함. Workbench에서는 같은 파일을 순서대로 열어 실행함. 앱 계정에는 테이블 생성·삭제 권한을 부여하지 않으며, 초기 SQL은 관리자 계정으로 적용함.

### 시연·테스트 데이터

| 파일 (`backend/database/`) | 용도 |
|---|---|
| `schema.sql` | 기존 모델링에 따른 테이블·제약·인덱스를 생성함 |
| `seed_reference.sql` | 공항·항공사·회원 등급을 등록함 |
| `seed_demo.sql` | 기본 데모 회원·항공편·좌석·예약을 등록함 |
| `seed_flights_202611_202701.sql` | 일반 여객 공항의 2026-11-12~2027-01-31 항공편·좌석을 추가함 |
| `seed_promotions.sql` | 시연용 프로모션을 추가함 |
| `seed_route_test.sql` | 인기·자주 이용한 노선, 회원·비회원 예약과 문의 테스트 데이터를 추가함 |
| `cleanup_route_test.sql` | 위 노선 테스트 전용 데이터를 삭제함 |

추가 시드는 필요한 파일만 적용함. 프로모션 시드는 `USE airline_reservation;`로 DB를 선택한 뒤 실행함. 날짜가 정해진 항공편·프로모션은 시연 시점에도 유효한지 확인함. 노선 테스트 파일은 관리자 계정에서 파일 전체를 실행하며, 삭제 파일은 다른 기본 시드까지 삭제하지 않음. 테스트 계정으로 별도 작성한 예약·문의가 있으면 먼저 확인·정리해야 함.

`seed_route_test.sql` 적용 후 사용할 테스트 계정은 다음과 같음. 기본 `admin`·`testuser`의 존재 여부와는 별개임.

| 계정 | 비밀번호 | 확인할 기능 |
|---|---|---|
| `ux26_member_a`, `ux26_member_b` | `UxDemo2026!` | 이용 기록·문의가 있는 회원 |
| `ux26_new` | `UxDemo2026!` | 기록이 없는 회원 |
| `ux26_admin` | `UxDemo2026!` | 관리자 기능 |

비회원 예약은 `UX26R011` 또는 `UX26R012`, 이메일 `ux26_guest@example.invalid`, 전화번호 `010-0000-2609`로 조회함. 비회원 문의는 `901004`~`901006`, 비밀번호 `GuestDemo2026!`로 조회함. 모두 가상 테스트 데이터임.

## 4. 로컬 실행

### 백엔드 — `backend` 폴더

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
if (-not (Test-Path .env)) { Copy-Item .env.example .env }
```

`backend/.env`에서 다음 항목을 설정함. 기존 파일이 있으면 값을 유지하고 필요한 항목만 확인함.

| 설정 | 입력할 내용 |
|---|---|
| `DB_HOST`, `DB_PORT`, `DB_NAME` | MySQL 주소·포트·DB명 |
| `DB_USER`, `DB_PASSWORD` | 앞서 만든 앱 계정 |
| `JWT_SECRET_KEY` | 충분히 긴 무작위 비밀값 |
| `CORS_ORIGINS` | 프론트 출처 목록. 예: `["http://localhost:5173","http://127.0.0.1:5173"]` |
| `CHATBOT_ENABLED` | 챗봇 사용 시 `true` |
| `GEMINI_API_KEY`, `GEMINI_MODEL` | 백엔드 전용 키와 계정에서 사용할 수 있는 모델 ID |

현재 모델 기본 설정은 `gemini-3.5-flash-lite`임(빠른 답변 생성 속도, 무료 한도가 넉넉함). 실제 계정의 모델 사용 권한·요청 한도를 확인함. `CHATBOT_REQUESTS_PER_MINUTE`는 앱의 요청 제한이며 외부 API의 전체 할당량을 대신 관리하지 않음.

```powershell
.\.venv\Scripts\python.exe -m uvicorn app.main:app --reload --host 127.0.0.1 --port 8000
```

`http://127.0.0.1:8000/docs`에서 API 명세를 확인함. 실제 API 경로는 `/api`로 시작함. `GET /api/health`는 앱 실행, `GET /api/health/db`는 DB 연결 상태를 확인함.

### 프론트 — 별도 터미널의 `frontend` 폴더

```powershell
npm ci
if (-not (Test-Path .env.local)) { Copy-Item .env.example .env.local }
npm run dev
```

`.env.local`에 API 주소를 설정함. 기존 api/v1에서 api/로 변경됨.

```dotenv
VITE_API_BASE_URL=http://127.0.0.1:8000/api
```

터미널에 표시된 프론트 주소로 접속함. 기본 포트는 `5173`임. 환경변수 변경 후 해당 서버를 다시 실행함. API 주소를 생략한 개발 모드에서는 Vite가 `/api`를 로컬 백엔드로 전달함. `localhost`와 `127.0.0.1`은 서로 다른 출처이므로 CORS와 실제 접속 주소를 맞춤.

폴더 통합 전에 실행한 개발 서버는 종료하고 새 위치에서 다시 실행함. `.venv`, `node_modules`는 다른 PC로 복사하지 않고 위 설치 명령으로 준비함. `.env`, `.env.local`은 Git에 포함하지 않으며 Gemini 키·DB 비밀번호를 `VITE_` 환경변수에 넣지 않음.

## 5. 테스트 방법

### 자동 검사와 빌드

`frontend` 폴더에서 실행함.

```powershell
npm test
npm run build
npm run preview -- --host 127.0.0.1
```

`npm test`는 요청 조건·예약 요청·표시 규칙을 검사하며 실제 DB나 Gemini를 호출하지 않음. `build`는 `dist`에 배포 파일과 PWA 파일을 생성함. 개발 모드에서는 서비스 워커를 등록하지 않으므로 PWA는 preview 또는 배포 주소에서 확인함.

### 실제 API 연결 점검

| 대상 | 확인할 내용 |
|---|---|
| 연결·인증 | `/api/health/db`, 회원 로그인, 비회원 조회, 관리자 권한을 확인함 |
| 검색 | 도시·코드 자동완성, 날짜·항공사 필터, 편도·왕복 결과를 확인함 |
| 예약 | 등급별 좌석 선택, 탑승객별 왕복 좌석 연결, 예약자 정보 복사, 금액·할인·포인트를 확인함 |
| 예약 검증 | 같은 좌석 경쟁, 동일 요청 재전송, 왕복 한 구간 실패와 전체 취소를 테스트 데이터로 확인함 |
| 문의·관리자 | 회원·비회원 문의 조회, 관리자 답변, 항공편 관리, 프로모션 등록·수정·삭제를 확인함 |
| 챗봇 | 전체 노선 최저가, 항공사 제외, 날짜·목적지 변경 후속 질문, 왕복·프로모션·노선 추천을 확인함 |
| 모바일 | 좁은 화면에서 필터, 좌석 선택, 하단 예약 패널과 챗봇을 확인함 |

실제 API로 예약·취소·문의 등을 실행하면 DB에 반영됨. Gemini 테스트는 AI를 활용해서 자동으로 분당·일일 한도에 맞춰 순차 실행함. 기존 사례와 결과는 [챗봇_테스트_정리.txt](../backend/챗봇_테스트_정리.txt)에 보관함. 자동 프론트 검사만으로 MySQL 동시성이나 AI 답변 정확성이 검증되는 것은 아님.

### PWA 점검

1. 온라인으로 접속한 뒤 개발자 도구의 Application에서 manifest·서비스 워커·아이콘을 확인함.
2. 브라우저의 앱 설치 기능으로 설치·독립 창 실행을 확인함. iOS는 Safari 공유 메뉴의 홈 화면 추가를 사용함.
3. 캐시가 준비된 상태에서 오프라인으로 전환하고 `/login`, `/inquiry`를 새로고침함. 화면과 연결 끊김 안내를 확인함.
4. Cache Storage에 API 응답이 없는지 확인함. 연결 복구 후 실패했던 예약·문의가 자동 등록되지 않아야 함.
5. 새 버전 배포 후 업데이트 안내의 나중에·새로고침을 확인함. 나중에는 입력이 유지되며 새로고침 시에는 초기화됨.

## 6. Vercel·ngrok 시연 배포

통합 폴더 `항공권 예매 서비스`를 저장소 루트로 사용하는 경우를 기준으로 함.

| Vercel 항목 | 설정 |
|---|---|
| Root Directory | `frontend` |
| Framework Preset | Vite |
| Node.js | 24.x |
| Install Command | `npm ci` |
| Build Command | `npm run build` |
| Output Directory | `dist` |
| 환경변수 | `VITE_API_BASE_URL=https://공개된-백엔드-주소/api` |

상위 작업 폴더 전체를 저장소로 사용한다면 Root Directory를 `항공권 예매 서비스/frontend`로 지정함. 소스·설정·`package-lock.json`은 포함하고 `.env*`의 실제 설정 파일, `.venv`, `node_modules`, `dist`는 제외함. `.env.example`은 포함함.

1. PC에서 MySQL과 FastAPI를 실행함. ngrok 인증 키를 이미 등록했다면 별도 터미널에서 `ngrok http 8000`을 실행함.
2. ngrok에 표시된 HTTPS 주소 뒤에 `/api`를 붙여 Vercel 환경변수에 입력함. 로컬 `.env.local`은 Vercel로 자동 전달되지 않음.
3. 백엔드 `CORS_ORIGINS`에 실제 Vercel 프론트 출처를 추가하고 백엔드를 다시 실행함. CORS 주소에는 `/api`나 끝의 `/`를 붙이지 않음.
4. Vercel에서 배포 후 `/login`, `/inquiry` 직접 접속·새로고침, 검색·로그인·예매를 확인함.
5. ngrok 주소가 바뀌면 Vercel 환경변수도 수정하고 다시 배포함.

시연 중에는 PC의 MySQL·FastAPI·ngrok을 계속 실행함. Vercel에는 프론트만 배포하며 MySQL 포트를 외부에 공개할 필요는 없음. 배포 프론트에서 API 환경변수를 생략하면 별도 프록시가 없는 한 데이터 호출이 동작하지 않음.

| 증상 | 확인할 항목 |
|---|---|
| 백엔드 시작 시 설정 오류 | `backend/.env`의 DB 계정·JWT 비밀값을 확인함 |
| 화면은 열리지만 데이터가 나오지 않음 | API 주소의 `/api`, 서버·ngrok 실행 상태, HTTPS, CORS를 확인함 |
| 항공편·프로모션이 나오지 않음 | 시드 적용 여부와 검색·프로모션 유효 기간을 확인함 |
| API 주소 수정이 반영되지 않음 | 개발 서버 재시작 또는 Vercel 재배포 여부를 확인함 |
| PWA 설치·업데이트가 보이지 않음 | HTTPS 또는 localhost, 배포용 빌드, 기존 설치·서비스 워커 상태를 확인함 |
